## (b) THE BUILD — Kit 3, Session 3: Build Your First Classroom Tool

### The title

**`Vibe Coding Staff PD | Build a Review Game with AI | Editable Slides & Script`** (77 characters)

"Vibe Coding" is required here because this session's lab ends in a working
file. Session 4 (student data) and Session 5 (leading adoption) will not
carry it. The store rule against leading with bare "ai" is respected —
"with AI" is qualified and mid-title.

Alternative at exactly 80, to use only if `review game` comes back strong and
thin: `Vibe Coding PD | Every Teacher Builds a Review Game | Slides, Script & Game File`.

### What every teacher walks out holding

**A review game file for their own subject, on their own device, that runs
with the wifi down.** Not a handout about AI. Not a list of prompts. A file
they can project on Friday.

That is the sentence the whole kit is for, and it is the one line on the
admin one-pager that closes the purchase order.

### Why the lab builds a game and not a tracker

Monday's recommendation said Session 3 should build a game **"if the game
converts well."** That condition cannot be evaluated: **drop 57 has not been
uploaded, so there is no conversion data at all.** Deciding anyway, and
saying so:

- **A PD's real job is to make forty teachers want to do this again.** The
  mechanism for that is excitement, and a staff room where every person
  leaves with something playable is a session people talk about in the
  parking lot. A behavior tracker is a chore, however useful.
- **A game is subject-neutral.** Forty teachers across every department each
  leave with something for their own content. A tracker fits some rooms.
- **A game fails visibly and safely.** When the AI gets something wrong in
  front of the room — and it will — a wrong color or a broken button is a
  teaching gift. The same mistake in a behavior tracker is a data problem.
- **It knows nothing about any child**, which makes it the safest possible
  artifact to build live in a room full of staff. See section (d).

### The time problem, and the resolution — read this before writing the clock

`kits/KIT_STANDARD.md` locks the session at **45–60 minutes** with a
protected lab of **at least 15 minutes**. `vibe-coding-line.md` and the
Wednesday routine both say "a facilitated ninety minutes". These conflict.

**The kit standard wins and is not amended.** Its lab figure is a floor, not
a ceiling, so a build session fits inside it without changing anything:

| Block | Minutes | Ends with |
|---|---|---|
| Welcome and why now | 4 | Why this room, this year, and who is paying for it |
| The one idea | 14 | Describe, build, test, change one thing — on the board |
| Guided practice, everyone together | 6 | Every laptop in the room has made the same one change |
| **LAB — protected** | **30** | **A game file on each person's own device** |
| Honest limits and commitments | 4 | What this does not do, and one thing each person will try |
| First 48 hours and exit ticket | 2 | The sheet and the ticket in hand |

Sixty minutes exactly.

**The standard's printed 45-minute cut is still required, and it costs the
lab two minutes.** Welcome 3, the one idea 8, guided practice folded into the
demo and gone, **lab 28**, limits and commitments 4, first 48 and ticket 2.
That is 45 with the lab still protected at nearly full length, which is the
point: discussion is what gets cut, and the printed cut has to show that
rather than assert it.

Also print a **90-minute extended column** for schools that hand over a full
PD block: 25 of the extra 30 minutes go to the lab (55 total) and 5 to a
share-out at the end, where three people project what they made. That is a
column in the prep guide, not a tenth file.

### The lab has two tracks, and Track 1 is the default

A facilitator cannot debug forty blank-page builds in thirty minutes. That is
the failure mode that ends this session badly, and the design answer is to
remove it rather than to hope.

- **Track 1 — start from the starter file.** The kit ships a working review
  game. The teacher opens it, replaces the questions with their own, changes
  the title, then makes **two real changes by prompting** — one cosmetic, one
  behavioral. Everyone finishes. This is the default and the script presents
  it as the normal path, never as the easier one.
- **Track 2 — start from nothing.** For the three or four people in every
  building who will want it. One page in the handout, the full first prompt
  written out, and the facilitator does not hover.

**Say plainly in the deck, the script and the description what the teacher
did and did not build.** They changed a working program by describing what
they wanted, which is the transferable skill and the whole point of the
category. Claiming they wrote it from scratch would be a lie a buyer catches
in the preview, and the honest version is a better lesson anyway.

**This is also the upsell, stated once and never as a promise of future
content:** the session teaches the pattern; the $19–24 Lane A build-alongs
already in the store teach building one from nothing.

### The starter file — build it first, and here is the argument

The routine's job 2 says deck and script only. **Recommendation: build the
lab's starter game file this Wednesday anyway, before writing the script.**

Nothing ships either way, so the letter of the routine is satisfied. The
reason is drift: a word-for-word script keyed to a file that does not exist
yet will describe buttons that end up named something else, and next
Wednesday somebody has to find every one of those lines. The game code
largely exists already — `kits/tpt-vibe-expedition/` and
`kits/tpt-vibe-review-game/` — so this is an adaptation, not a new build.

If the file is not built this run, then **next Wednesday's first task is to
re-check every script line against the built file and fix the drift**, as an
explicit task, not a hope.

**What the starter file must do**, so the script can be written against it:

- One HTML file, opens by double-click, no install, no account, works offline.
- **The teacher's questions live in a clearly marked block at the very top**,
  in the same shape as the shipped games: eight to ten entries, each with the
  question, the answers, and one line saying *why* the right answer is right.
- A generic set of questions ships in it so that a teacher who arrives with
  nothing still has a working game in the first two minutes.
- Passes `tpt/intel/GAME-DESIGN-STANDARD.md` in full. That is binding and it
  is not relaxed for a PD file: competence first, a real decision every turn,
  no public individual ranking, no mechanic where one student's miss visibly
  costs the group, missed ideas come back later in the session, and the
  biggest celebration in the game belongs to the student who was wrong and is
  now right.
- **No pixel art.** Gradients, sine ridges, silhouettes, a rim light. A
  teacher who will not project it will not use it, and a facilitator standing
  in front of a staff room cannot recover from ugly.
- **No name field anywhere, and no high-score table.** See section (d).

### The script — around 10 pages, word for word

Keyed to slide numbers, with stage directions and a running clock, exactly as
Kit 1 and Kit 2 are built. Three things this script needs that theirs did not:

1. **A recovery line for every predictable break.** "It gave me a blank
   page." "It changed the wrong thing." "My questions disappeared." Each one
   gets a sentence the facilitator says out loud and a fix that takes under
   thirty seconds.
2. **A scripted moment where the AI is wrong on purpose.** The facilitator
   makes a vague request on the board, gets something unhelpful, and names
   what was missing. This is the most valuable ninety seconds in the session
   and it cannot be left to chance.
3. **A three-minute "write four questions now" beat** before the lab, for
   everyone who came empty-handed. The prep guide asks people to bring eight
   to ten review questions; some fraction will not.

## (d) DESIGN, SAFETY AND THE RULES THAT DO NOT BEND

### Verify every statistic, or cut it

This is the lane where one invented number ends the account. The mandate
figures in this brief came from web research on 2026-09-21 and **the factory
must verify each one against a live source before it reaches a slide**, with
a full APA entry in the references file and a "used for" note.

Specifically: Maryland SB 720 and its 1 July 2027 date · the Virginia and
Ohio 2026 laws · "more than 70 bills across 27 states" · the compensation
and no-charge provisions · "most districts remain underprepared."

**Anything that cannot be verified today comes out of the deck.** A slide
with four solid citations beats a slide with seven where one is wrong. If a
figure is cut, say so in the run summary.

### The data rule, sized to this session

The tier is decided by **where the data lives and who can reach it**, not by
whether names appear. This session is unusually easy on that axis and the
product should say why:

- **Tier 1 — build freely.** Questions, answers, the why-line, the title, the
  colors. All teacher-authored, none of it about any child.
- **Tier 2 — the teacher's own device.** The file itself, saved where they
  keep their own work. It transmits nothing because there is nowhere to send
  it.
- **Tier 3 — stop and ask the district.** The moment a child's name, score,
  IEP status, behavior record or writing sample enters a prompt. Nothing in
  this session requires that, which is exactly the point.

**No child's data appears in any demonstration, including the facilitator's
own class.** The demo questions are about a made-up unit.

### The high-score table is refused in the product, and the reason is given

The first feature request from any staff room will be a leaderboard with
student names. **The game refuses it**, and the kit explains: it would put a
child's name and performance into a file that gets emailed around, and public
individual ranking is the mechanic that does the most damage to the students
who are already struggling. That is in `GAME-DESIGN-STANDARD.md` and it holds
here.

Saying no to an obvious feature, with a reason, is a differentiator. It is
the posture every product in this catalog takes.

### The facilitation hazards, each with its fix

1. **Nobody brings questions.** The prep guide asks for eight to ten; expect
   a third of the room to arrive empty. Fix: generic questions ship in the
   starter file, and the script has a three-minute writing beat.
2. **The school blocks the AI tool.** Fix: the prep guide has the facilitator
   check the tool from a staff machine, on the school network, in the room,
   the week before. This is task one of the prep guide, not a footnote.
3. **Forty people on one wifi access point.** Fix: the file runs offline once
   it exists; only the prompting needs the network. Say so, and stagger.
4. **A wide skill spread in one room.** Fix: the two tracks, and a named role
   for the confident people — they help the table next to them, which is also
   how a building gets its second facilitator.
5. **The AI rewrites the whole file and loses the teacher's questions.** The
   single most likely real failure. Fix: save a copy before prompting, taught
   as a step and not as a tip, plus the recovery line in the script.
6. **The session runs long and the lab gets cut.** Fix: the lab is protected
   in writing, the 45-minute cut is printed, and the script says what to drop.

### Standing Lane C rules

- **Presentable cold.** A teacher-leader who has never run a PD can deliver
  it from the script alone.
- **A live AI mistake is a teaching gift** — the script says so and tells the
  facilitator what to do with it.
- Nine files exactly, copying Kit 1 and Kit 2's file set and naming.
- Voice per `kits/KIT_STANDARD.md`: warm colleague, no hype, almost no em
  dashes, "AI drafts, the teacher decides."
