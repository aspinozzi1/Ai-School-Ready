## Before the phrases: a product problem Friday has to solve

Lane B build 3 in the spec is **"Test it like a user"** — usability testing,
feedback rounds and iteration, the part schools never teach. It is the right
next unit and it has a hole in it.

**Builds 1 and 2 each shipped their own working app. Build 3 tests an app the
buyer may not have.** A teacher who did not buy Pitch to Prototype or The Class
Store opens this unit with nothing to test, and a unit whose first instruction is
"use the app you built in a different product" is one a buyer feels cheated by.

### The fix, and it is better than a workaround

**Ship an app to test — and ship it deliberately broken.**

Not badly made. **Made with real, findable usability problems in it**, of the
kind every first build has: a button whose label does not match what it does, a
step that needs explaining, a confirmation that never comes, an error that says
nothing useful, something that works only if you already know the order.

Students cannot find usability problems in a polished app, and a class that finds
nothing concludes testing is a formality. **A deliberately flawed app is the only
way this unit reliably works** — and the teacher's guide can list what is wrong
with it, so the teacher knows what their class should be finding and can tell
whether the testing is working.

**That is also the honest version of the lesson.** Real software is like this.
The point is not that somebody built it badly; the point is that you cannot see
these problems from the inside, which is the whole reason user testing exists.

I am recording this as a recommendation rather than a decision taken, because it
changes what the product *is*. **Thursday's brief will carry it unless you say
otherwise.**
