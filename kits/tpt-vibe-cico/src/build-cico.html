The real-world shape this fits

Check-in, check-out (CICO) is, by the research literature, the most frequently used Tier 2 behavior support in US schools: a student checks in with an adult, is scored on a small set of expectations through the day, checks out, and a copy goes home — typically run for six to eight weeks and reviewed on the data it produces. This pack does not teach CICO as an intervention. It builds the card that any team using a structure like it would actually need.

Why this build matters

A tally tells you today. A record tells you the truth.

Build 2's points tab keeps a running total per student and nothing else — no dates, no history, no way to answer "is this better than three weeks ago." That is a tally. This build is the step up from it.

A tally

One number per student that goes up. Ask it "how was Tuesday?" and it has no answer — Tuesday was overwritten the moment Wednesday happened.

A record

A list of dated entries: this student, this day, this time block, this expectation, this score. The day total, the week trend, and everything else in this pack are computed from that list — they are never the thing being saved.

Say this sentence to yourself before you open the chat.
"I am not asking it to remember a number. I am asking it to remember a list of dated entries, and compute the numbers from the list." That one sentence is the entire architectural idea in this pack, and once you have built it here you can put it in anything: attendance, reading minutes, incident logs.

Why a tally is the trap, not a shortcut

Left to its own judgment, an AI chat will very often build the tally — it is simpler and it looks finished sooner. It works fine for a week. Then a colleague asks "is this better than last month" and there is no way to answer, because last month was never kept. By the time a teacher notices, they own three weeks of data that cannot answer the one question the whole tool exists for.

What this costs you

One extra idea to hold in your head at task 4, and slightly more code than a tally would need. That is the entire price for data that can actually answer a question about the past. Task 4 walks it through slowly, once, and you will not need to think about it again after that.

Read this before you type a single score

The three tiers, made stricter for a behavior record

The tier is decided by where the data lives and who can reach it, not by whether a name appears — the same rule as every pack in this series. For this build the answer is stricter, because a dated behavior record about an identified child is more sensitive than a class roster.

1

The card design

The expectations, the goal percentage, the blank printable layout. All teacher-authored, no student in it. Build freely.

2

Daily scores, by student number, on this device

The app's home. Kept in this browser, on this device, transmitted nowhere. The app defaults to student numbers rather than initials, and that default is the right choice, not a setting to change.

3

The moment those records leave the device

Synced, emailed, dropped in a shared drive, pasted into a chatbot, or opened on a computer somebody else signs into. Stop and treat it as a conversation with your district, not a setting you flip.

One more line, specific to this build

This tracker is your own working record, not the school's record of behavior. If your district keeps an official behavior or IEP data system, that system is the record of record. This tool is the fast, private, day-to-day version that feeds your own thinking between the meetings where the official record gets updated.

So the rule is not "never track behavior on a computer." It is: records may live locally, by student number, on your own device; they may not be published, synced, or pasted into a chatbot. The export tab exists so the safe route — a private backup file on your own drive — is also the easy one.

Practical guidance, not legal advice. FERPA, COPPA, your state law and your district's policy are the authorities. If you are unsure, use a student number instead of initials — the tracker works exactly the same either way.

Task 1

The shell and the roster

Prompt 1 · the shell and the roster
Build me a behavior point tracker as one single HTML file I can save and open in a browser.

It has six tabs across the top: Roster, Expectations, Score today, Week view, Print a card, and Data and export. Clicking a tab shows that panel and hides the others.

In the Roster tab: a text box and an Add button for adding one student at a time, shown afterward as a list with a small remove button on each. The box is labeled "Student number or initials" — never a full name field.

Requirements:
• Everything in ONE file — styling and code included. No internet, no login, no account.
• Big text and big buttons; a teacher will use this at a desk, not across a room.
• Leave the other five panels empty for now with just their names in them.
• Nothing is sent anywhere and nothing asks for a password.

That "never a full name field" line is not a style choice

A dated behavior record is more sensitive than a class list, and this pack's whole privacy posture depends on the roster never holding one. Say it in the prompt so the model does not default to "Student name" out of habit.

Task 1 is done when

You can click all six tabs and watch the panel change, and you can add a student to the roster and see them appear in a list. Nothing needs to save yet — that is task 4.

Task 2

Name the expectations

Every point card is scored against a short, specific list — the same three to five things, every block, every day. Naming them well is most of the design work.

Prompt 2 · the expectations
In the Expectations tab: a text box and an Add button for adding one expectation at a time, shown as a list with a remove button on each. Allow no fewer than one and no more than five. Also add a number box for "daily goal" as a percentage, defaulting to 80.

Write these in your own words, not a behaviorist's

"Followed directions the first time," "kept hands and feet to self," "used a calm voice" — short, positive, specific enough that you and a substitute would score the same moment the same way. Vague expectations ("behaved well") make every score a guess.

Why cap it at five

More than five expectations turns a thirty-second check-in into a form, and the tool stops getting used by week two — the same failure mode as scoring too many blocks, covered on page 19. Five is already generous; most real point cards use three or four.

Task 2 is done when

You can add, see, and remove expectations, a sixth is refused with a message rather than silently accepted, and the goal box holds a percentage.

Task 3

The day grid

Prompt 3 · the scoring grid
In the Score today tab: a dropdown to choose which student you are scoring, and below it a grid with time blocks as rows and the expectations as columns. Use three time blocks: Morning, Midday, Afternoon. Each cell is a button. Clicking a cell cycles it through no score, 2, 1, 0, and back to no score, and shows the current value.

Why a tap-to-cycle button beats a dropdown per cell

A teacher scoring a real student mid-lesson has three to five seconds, not thirty. One tap per cell, repeated until the number they want shows, is the fastest input shape there is for a small fixed set of values. A dropdown or a typed number is slower for exactly the same result.

What 2, 1 and 0 mean

This follows the scale most point cards already use: 2 met the expectation, 1 needed a reminder, 0 did not meet it this block. You are not required to use this scale — say so in the prompt if your school's card uses something else, like a smiley scale or a 1–5 range.

Task 3 is done when

With one student selected, you can tap through a full grid of blocks and expectations and watch each cell's number change. Nothing needs to survive a reload yet.

Task 4 — the important one

Make it remember — a shape, not a number

Everything else in this build is ordinary. This is the step that makes it software, and it is harder than build 2's version of the same idea.

Prompt 4 · saving a record, not a total
Now make this tracker remember its data between sessions, using the browser's local storage on my own device. Nothing should be sent to a server and there should be no account.

Save the roster, the expectations, the goal, and every scored cell as its own dated entry: which student, which date, which time block, which expectation, and what score. Do not collapse these into a running total — keep every entry, tagged with its own date, so a day two weeks ago can still be looked up on its own.

Important:
• Save whenever anything changes, automatically. I should never press a Save button.
• Load whatever was saved when the page opens.
• If saving or loading fails for any reason, the app must still work with empty data rather than showing an error or a blank screen.
• Only a scored cell should count in any later total — an unscored cell must not count as a zero.

Read that fourth bullet again

It is the same idea as build 2's failure-case instruction, and it matters even more here: a managed school device can restrict local storage, and a private window blocks it outright. Without this line the app can crash on open. With it, the worst case is a blank day — annoying, not broken, and nothing already saved is lost.

Task 4, continued

The test that proves it kept the shape

Do this exactly

1. Score two or three cells for one student today.
2. Close the tab completely. Not refresh — close it.
3. Open the file again and select the same student.

Today's scores should still be there, exactly as you left them. If they are, you have built an application that remembers a record. If they are not, task 4 is not finished and nothing in tasks 5 through 9 will produce a trustworthy number.

If the test fails
I closed the tab and reopened the file, and my scores were gone. Every scored cell should have been saved as its own dated entry to local storage on this device and loaded again when the page opens. Fix that and give me the whole file back.
A second test worth running, once the first one passes
Score one student for today, then change your computer's clock forward one day and score them again. Go back to today's date in the app if it lets you, or just check tomorrow. Confirm both days show up separately in whatever you build in task 6 — if only the most recent day appears, it is still keeping a total, not a record, and that is worth catching now rather than in week three.
Do not move past this page until the first test passes. Every later task reads from the same saved list. Debugging the week view while also debugging whether entries persist at all is much harder than confirming persistence on its own, once, here.

Task 5

The day roll-up

One number per student per day, computed from the list task 4 just built — never saved on its own.

Prompt 5 · earned over possible
Add a day summary under the grid in the Score today tab. Count only the cells that have been scored today for the selected student: add up the scores for "points earned," and multiply the number of scored cells by 2 for "points possible." Show earned, possible, and the percentage, next to the daily goal.

Why "possible" is not just "blocks times expectations"

A day where only nine of fifteen cells got scored — a fire drill ate the afternoon, say — is not the same shape as a full day, and comparing its raw percentage to a full day's is comparing two different things. Counting possible points only from cells that were actually scored keeps the fraction honest on a short day. This is the failure mode on page 19 that this exact design choice prevents.

Task 5 is done when

Scoring three cells at level 2 for a student with nothing else scored shows "6 of 6" and 100%, not "6 of 30."

Task 6

The week view

Prompt 6 · five days, one table
In the Week view tab: a table with one row per student and one column per weekday, Monday through Friday, for the current week. Each cell shows that day's percentage from the roll-up in task 5, or a dash if that day was not scored. Color a cell green if it meets the daily goal and a different color if it does not. Add a week average column.

What "the current week" should mean

Ask for Monday through Friday of the week containing today. On a weekend, that naturally shows last week's finished data rather than an empty week that has not started — useful on a Sunday night, and worth asking for by name if the first version does not do it.

Task 6 is done when

You can look at the table and answer "is this student better than three weeks ago" without opening a single day — the exact question a tally could never answer, now sitting in one row.

Task 7

Export, and the habit that protects six weeks of work

Everything this pack has built lives in one browser on one device. That is also its only real weakness, and this task is the fix.

Prompt 7 · export and a weekly reminder
In the Data and export tab: a button that downloads everything — the roster, expectations, goal, and every dated entry — as a single file to my computer. Also: remember the date of the last export, and show a visible message anywhere in the app if it has been seven days or more since the last one, or if none has ever been done.

Why this task is not optional

A CICO card typically runs six to eight weeks. Clearing browser data, a laptop replacement, or a school re-image wipes local storage completely and without warning — and the whole value of this tool is the trend line across those weeks. Pick a day — the brief suggests Friday afternoon — and export every single week. It takes ten seconds and the app now tells you when you are overdue.

Task 7 is done when

Clicking export downloads a file you can find in your downloads folder, and the reminder message appears the first time you open the app before ever exporting.

The printable day card

Prompt 8 · one page, one child
In the Print a card tab: a dropdown to choose a student and a button that opens the print dialog with a single clean page showing that student's name or number, today's date, the scoring grid with today's numbers, the day total, and two blank signature lines: one for the adult, one for "sent home." Task 10

Colors, accessibility, and the shared-computer check

Prompt 10 · make it yours, and make it safe on a shared machine
Restyle the tracker with [your colors]. Then make sure everything works for someone using a keyboard instead of a mouse: every tab, button and dropdown reachable with Tab, usable with Enter, with a clearly visible outline on whatever is selected. Do not rely on color alone to show a score — keep a number or a symbol on every cell as well as its color.

The check this task adds that build 2 did not need

Browser storage is per browser profile, not per person. A substitute, a co-teacher, or a student using the same login on the same classroom machine can open this tracker and see it. Before you rely on it: confirm the computer you use it on is signed into a profile only you use, the same way you already treat a locked filing cabinet. This is the single biggest hazard specific to this build, and it does not apply to a name picker or a class list.

How to check the keyboard part actually worked

Put the mouse down. Press Tab repeatedly — a clear outline should move between tabs, the dropdown, and every grid cell. Press Enter on a cell — it should cycle its score. If either fails, say exactly that and ask again.

You can score a full day using only the keyboard, and you have said out loud which computer this will live on and confirmed it is not a shared login.

Saving and using it

Out of the chat, into your room

1. Copy all of the code

Use the copy button on the code block. Selecting by hand usually misses the last line.

2. Paste into a plain text editor

Notepad, or TextEdit set to plain text. Not Word — it adds invisible formatting that stops the file working.

3. Save as behavior-tracker.html

On Windows set "Save as type" to All Files so it does not quietly become a .txt.

4. Put it somewhere you will find it, then leave it there

Your saved records are tied to this file in this browser, on this device. Pick its home now and do not move it between machines expecting the history to follow — that is exactly what the weekly export from task 7 is for.

Make a bookmark. Open the file, then bookmark it like any web page. Now checking in is one click every morning, the same as any other tool on your bar.

When it breaks

The six things that actually go wrong

1. A different browser shows an empty tracker

Almost always a different browser, a private window, or a browser set to clear site data on exit. Check you are opening the exact same file the exact same way as before. Nothing is lost — you are looking in a different notebook. This is why the weekly export in task 7 exists.

2. It saves, but not on the school laptop

Some managed devices restrict local storage by policy. If the app still works but forgets, that is the cause, and it is exactly why task 4's prompt asked for it to keep working with empty data rather than crash. Ask your tech team; it is usually a setting they can adjust.

3. Scoring every block for every child gets abandoned by week two

This tool is built for one child's card at a time, three to five expectations, a few taps — not a whole class scored every hour. If it feels slow, you are likely using it for more students or more blocks than a point card is meant to hold. Say: "Scoring takes too long. Cut it down to what one adult can realistically do in the moment."

4. A day with fewer blocks scored looks unfairly low

This is the changing-denominator problem task 5 was built to prevent. If a percentage looks wrong on a short day, check that "points possible" is counting only scored cells, not every cell on the grid. Say: "An unscored cell must not count as a zero in the daily percentage."

5. The de-identified summary still shows a real number or initials

Stop and fix this before sharing it anywhere. Say: "The summary still has a real student number in it. Every student must be relabeled S1, S2, S3 before the text is shown." Then check it again by eye.

6. It worked, then an edit broke it

Paste the part you changed into the chat and say "something in this is broken, find it." You do not need to spot it yourself, and you do not need to re-explain the whole app — the broken piece is usually enough.

What changes the moment any of this goes online

The data stops living on your device and starts living on someone's server. A link exists that could reach it. The file

The part that keeps the shape

The complete tracker ships with this pack as behavior-tracker.html — you do not need to type any of this. This is the piece worth reading, because the same shape belongs in anything you build next that needs a history rather than a total.

/* ---- storage: one key, this browser only ---------------------------- */ const KEY = 'vibe-cico-v1'; const blank = { students: [], expectations: ['Followed directions', 'Kept a calm voice', 'On task'], blocks: ['Morning', 'Midday', 'Afternoon'], goal: 80, entries: {}, lastExport: null }; let storageOK = true; let S = load(); function load(){ try { const raw = localStorage.getItem(KEY); if (!raw) return { ...blank, entries: {} }; const o = JSON.parse(raw); return { students: o.students || [], expectations: (o.expectations && o.expectations.length) ? o.expectations : blank.expectations.slice(), blocks: (o.blocks && o.blocks.length) ? o.blocks : blank.blocks.slice(), goal: o.goal || 80, entries: o.entries || {}, lastExport: o.lastExport || null, }; } catch (e) { // private window, blocked storage, corrupt value storageOK = false; return { ...blank, entries: {} }; } } function save(){ try { localStorage.setItem(KEY, JSON.stringify(S)); } catch (e) { storageOK = false; } document.getElementById('storageBanner').hidden = storageOK; checkExportBanner(); }

Reading it without knowing code

Every entry is stored under a key built from the date, the student, the block, and the expectation — so each dated fact gets its own slot instead of overwriting the one before it. load hands back empty data if anything at all goes wrong reading storage; save writes the whole object and quietly gives up rather than crashing if the browser refuses. Both are wrapped in try and catch, which is task 4's instruction — keep working when storage is unavailable — showing up as real code.
