The one idea

Three layers, and none of them trusts the others

Most software protects student data by being careful. Careful software has a bad day eventually. This one is built so the bad day is boring.

1

The browser shortens the name

You paste Anthony Spinozzi. Before anything is sent anywhere, the page turns it into Anthony S. The surname never leaves the computer you typed it on.

2

The database refuses the long form

One line of the table definition says what a name is allowed to look like. Send Anthony Spinozzi anyway — by accident, by a bug, by pasting into the wrong box — and the database rejects it. Not a warning. A refusal.

3

There is nowhere to put one

No column in the whole database is for a last name. Even if somebody wanted to store one, there is no shelf to put it on.

Each layer is independent, and that is the entire point.
Layer 1 is code you wrote, so it can have a bug. Layer 2 is a rule the database enforces whatever your code does. Layer 3 is the shape of the thing itself. For a surname to end up stored, all three have to fail at once — and they fail in different ways for different reasons.

Why this is worth doing properly once

You can reuse this pattern in everything you build afterwards. Decide what the tool must never know, then make it structurally unable to know it. That habit is worth more than any single tool in this series.

Task 1

Decide what this tool will never know

Before a single prompt. This takes four minutes and it is the only task that cannot be done by the AI.

Write down one sentence

"This roster knows <what> and never knows <what else>."

Mine is: it knows a first name and a last initial, and it never knows a surname, a student ID, a grade, or a birthday.

Why the sentence comes first

If you start prompting without it, the AI will helpfully offer you an email field, a parent contact field and a notes box, because that is what rosters usually have. Every one of those is a thing you would then have to protect. The cheapest student data to keep safe is the kind you never collected.

The test for whether a field belongs

For each thing you are tempted to store, ask: what does this tool do differently because it knows that?

A roster does nothing differently for knowing a birthday. So it does not get one. If you cannot answer the question, delete the field.

This is also the answer you give an administrator. Not "it is secure" — that is a claim you would have to defend. "It cannot hold that" is a fact about the thing, and you can show them the line that makes it true.

Task 3

The two tables

Two tables is the whole database: classes, and the students in them.

Prompt 1 · the tables
Write me a Postgres schema for a class roster, as SQL I can paste into the Supabase SQL editor. Two tables. classes: id, name, an optional period, an archived flag, created_at. students: id, class_id referencing classes with on delete cascade, display_name, a sort_order integer, created_at. Use uuid primary keys with gen_random_uuid(). Make display_name unique within a class. Do not add any other columns — no email, no student number, no notes. Add a comment at the top saying why there is no column for a last name.

What you should get back

About twenty lines of SQL. Read it before you run it. You are looking for two things: that students has exactly the columns you asked for, and that on delete cascade is on the class reference — that is what makes deleting a class in June actually delete its students.

Run it

Supabase, SQL Editor, paste, Run. Then Table Editor, and look at them. Seeing the empty tables is the point of the task.

If it added columns you did not ask for

It will sometimes add email or full_name anyway, because that is what most rosters look like. Delete those lines yourself before running it. This is the first place the habit from task 1 earns its keep.

Two tables exist and you have looked at them.

Task 4 · the one that matters

The line that makes the wrong thing impossible

Everything else in this build is plumbing. This is the product.

Prompt 2 · the constraint
Add a CHECK constraint to the students table called display_name_is_shortened. It must accept a single first name like Jo or O'Neal, or a first name followed by a single capital letter and a period like Anthony S., optionally followed by a number like Anthony S. 2. It must reject anything containing a full surname, including Anthony Spinozzi, Spinozzi, Anthony and Anthony S. Spinozzi. Also cap the length at 24 characters. Give me the ALTER TABLE statement and explain the pattern in plain English, one clause at a time.

What it looks like when it is right

constraint display_name_is_shortened check (
  display_name ~ '^[A-Za-z][A-Za-z''-]*( [A-Z]\.( [0-9]+)?)?$'
  and length(display_name) <= 24
)

The doubled quote inside the pattern is how SQL writes a single apostrophe, and it is what lets O'Neal through. If yours has one quote there, the statement will not run.

Now try to break it, in the SQL editor, before you build anything else

insert into students (class_id, display_name)
values ('00000000-0000-0000-0000-000000000000', 'Anthony Spinozzi');

You want the error. new row for relation "students" violates check constraint "display_name_is_shortened". If it stores instead, the constraint did not apply — check you ran the ALTER on the right table.

That error message is the thing you are building. Everything from here is a nicer way to avoid ever seeing it.

You have made the database say no to you, on purpose.

Task 5

A page that talks to it

One HTML file. It asks for your URL and key, then reads the classes table.

Prompt 3 · the page
Build a single HTML file, no frameworks and no build step, that runs by opening it in a browser. It has two boxes at the top for a Supabase project URL and an anon key, and a Connect button. It saves both to localStorage so I do not retype them, and it keeps working if localStorage is unavailable. On connect it reads the classes table through the Supabase REST endpoint using plain fetch — not the supabase-js library, since I am not installing anything — and lists the classes in a dropdown. Send the key in both the apikey and Authorization headers. If the request fails, show me the actual error message on the page rather than logging it to the console. Big text, big buttons.

The sentence that saves you twenty minutes

"not the supabase-js library, since I am not installing anything." Left to itself the AI writes import { createClient }, which needs npm, which needs a terminal, which is the cliff most teachers fall off. Plain fetch against the REST endpoint does the same job from a file you double-click.

Make one class so there is something to see

Easiest in the Supabase Table Editor: insert a row into classes with a name. Then reload your page.

Nothing appears and there is no error

Almost always Row Level Security. Supabase turns it on by default, and with no policy the anon key can read nothing — which looks exactly like an empty table. Prompt 4 on the prompts page fixes it, and the data page explains what you are turning on.

Task 7

Paste a whole roster at once

Nobody types thirty names one at a time twice.

Prompt 5 · the paste
Add a big text box where I paste a whole class list, one name per line, straight out of whatever my school system exports. Shorten every line in the browser, show the preview as a list of what I typed to what will be stored, and add an Add to class button that inserts them all in one request with their sort order. Ignore blank lines. After a successful add, clear the box and refresh the list. If the insert fails, say so and tell me nothing was added, because the whole request is one statement.

Why one request and not thirty

A single insert either takes the whole class or none of it. That is much easier to reason about than a run that half worked and left you guessing which fourteen students made it. The phrase "tell me nothing was added" in the prompt is what gets you an honest message instead of a cheerful one.

Task 8

Two students with the same short name

You have an Anthony Spinozzi and an Anthony Sanders. Both shorten to Anthony S. This is not an edge case; it happens in most classes of thirty.

Prompt 6 · collisions
Two students can shorten to the same name. When that happens, number them: the second Anthony S. becomes Anthony S. 2, the third becomes Anthony S. 3. It has to check against students already in the class, not only the ones in this paste, so adding a second Anthony next week still works. Show the numbering in the preview so I can see which is which before I commit.

The bug this prompt exists to prevent

Left alone, the code checks only within the batch you just pasted. Add Anthony Sanders in September and Anthony Spinozzi in October, and the October insert fails on the unique constraint with a message that will mean nothing to you at 7am. "Already in the class, not only in this paste" is the whole fix.

And now the awkward human bit

Somebody is Anthony S. 2 and they will notice. Tell them why on the first day: the tool does not keep last names, so it counts instead. Every student I have explained that to has thought it was reasonable. It is a better conversation than the one where a system holds their whole name for no reason.

Prompt 9 · the export
Add a button that copies the class to the clipboard as S1, S2, S3 in roster order, with no names at all. If the clipboard is blocked, show the text on the page so I can copy it by hand.

What this is actually for

Group arrangements, seating experiments, rotation schedules, anything where you want a second opinion from an AI about the shape of your class rather than about the people in it. You keep the S1-to-name mapping in your head or on paper. The chat never sees a child.

Task 12

What happens in June

The task everybody skips, which is why so much student data outlives the student.

Prompt 10 · the ending
Add an archive control for a class, and a delete that really deletes — the class and every student in it. Make delete ask me to confirm by typing the class name, because it cannot be undone. Then tell me in one sentence what happens to the student rows when a class is deleted, based on my actual schema.

The answer you want back

"The students are deleted too, because class_id references classes with on delete cascade." If the AI cannot tell you that from your own schema, ask it to look again — and if the cascade is genuinely missing, add it now rather than in June.

Archive and delete are different promises

Archive means out of my way. Delete means gone. Tools that only archive let data quietly accumulate for years, and a list of every child you have taught since 2026 is a thing you never decided to keep.

Put a date on it

Pick a day — the last in-service day works — and delete last year's classes on it. A retention habit is worth more than a retention policy, and this one takes four minutes a year.

Said plainly

The key in your file, and who can read your roster

This page exists because every other tutorial about this leaves it out.

The honest sentence

Anyone who has both your project URL and your anon key can read and change this roster. The policy you added in prompt 4 is what lets your page work, and it does not know the difference between your page and somebody else's.

So three things follow, and they are not optional

One. The file lives on your computer. Never on a website, never in a public folder, never pasted into a forum when you are asking for help — strip the key first.

Two. Nothing sensitive goes in this database. Look at what is actually in there: first names, last initials, and the order they sit in.

Three. If you ever think the key has got out, Supabase can issue a new one in a few seconds. Do that, then paste the new one into your file.

Now read those two sentences together, because this is the whole argument of the pack.
A leak is possible. What a leak would expose is a list that says "Anthony S." and "Maria C." You did not make the breach impossible. You made it boring. That is a far more reliable form of safety than being careful, because it keeps working on the day you are not.

What this is not

Not a system of record, not a gradebook, and not a replacement for whatever your district runs. It is a roster you own, for your own classroom, made out of information you already carry around in your head.

Where the data lives

The three tiers, for this build specifically

The tier is decided by where the data lives and who can reach it, not by whether names appear.

Tier 1 — build freely

The class name, the period, the structure of the tool, the schema, the code. All yours. None of it is about a child.

Tier 2 — where this roster lives

First names and last initials, in a database only you have the key to, on a page that never leaves your machine. This is the tier the whole build is designed to sit in, and the constraint in task 4 is what keeps it there instead of drifting up a tier the first time somebody pastes a full roster into the wrong box.

Tier 3 — stop, and ask the district

Anything traceable to a particular child beyond a name: grades, behavior records, IEP status, attendance, contact details. Also any of this once it is shared — a staff folder, an emailed export, a chatbot window, a second teacher's account. The data did not change. Who can reach it did, and that is what moves the tier.

The part people get backwards. Adding a database did not automatically push this build into tier 3. Sharing it would. A tool on a server that only you can reach is closer to a notebook in your desk than to a district system, and the difference is who holds the key.

Not legal advice

Your district's policy, your state's law, FERPA and COPPA are the authorities. This is a way of thinking that keeps you well inside them, not a substitute for asking.

Reading the error

Postgres is blunt, and that is a kindness

Database errors look frightening and are the most useful text in this whole build.

new row for relation "students" violates check
constraint "display_name_is_shortened"

Three pieces, left to right

new row for relation "students" — where it happened. Not classes, not somewhere mysterious. The students table.

violates check constraint — what kind of rule. A CHECK is a rule about the contents of one row, which means the problem is in the value, not in your connection or your key.

"display_name_is_shortened" — which rule, by the name you gave it in task 4. This is why naming constraints is worth the two extra words.

The other one you will meet

duplicate key value violates unique constraint
"students_class_id_display_name_key"

Same shape. The name tells you the columns involved: class_id and display_name. Two students in one class shortened the same way, and the numbering did not catch it.

The rule for getting help fast: paste the whole error, not a summary of it. The constraint name is the single most useful word in the sentence and it is the first thing people paraphrase away.

The first day

What to say to thirty students

You built a tool that treats them carefully. Tell them.

Sixty seconds, roughly like this

"This is the roster I use. It has your first name and the first letter of your last name, and that is all it has — not your ID, not your grades, not your birthday. It is set up so it cannot keep your last name, not just so I remember not to type it. If two of you come out the same it will number you, and that is why one of you is Anthony S. 2."

Why bother

Because students are told constantly that software watches them, and they are mostly right. Showing them one piece that was deliberately built to know less is a better lesson about technology than any unit on digital citizenship, and it takes a minute.

If somebody asks a hard question

"Could someone else see it?" is a fair question and the answer is yes, in principle, if they had my key — and what they would see is a list of first names. Answer it straight. A student who catches you overselling the safety of a system learns the wrong lesson very efficiently.

The ask worth making

Ask them what else the school stores about them, and who they think can see it. You will get a better discussion out of that than out of any prepared question.

Outgrowing it

When one file is enough, and when it is not

Honest answer: most classroom tools should be one file. This is not most tools.

Stay with one file when

Only you use it · only on one machine · losing the data would be annoying rather than serious · it is a timer, a picker, a generator, a checklist · you want it working in four minutes.

You have outgrown one file when

The same information has to be in front of two machines · losing it would cost you a real afternoon · something else you build needs to read the same list · it has to survive a browser being cleared by somebody else's IT policy.

The trap in between

Do not put a database behind something that did not need one. You will have taken on a key to protect, a service to remember, and a second thing that can be down, in exchange for nothing. The question is never "is a database better" — it is "what does this tool do that one file cannot."

The roster is the honest first case, because a class list is the thing every other classroom tool wants to read. Once it lives somewhere with a key, the next tool you build can use it instead of asking you to type thirty names again.

For the teacher

How this pack is built, and what it does not claim

Where this pattern comes from

It is not theoretical. The three-layer approach — shorten in the browser, refuse in the database, no column to put it in — is taken from software I built and run for my own high school woodshop course, which has been in daily use with real students for a full school year and is still being extended. The roster in this pack is that design, reduced to the smallest thing that teaches it.

What was actually tested before this went out

The constraint pattern was run against accepting and rejecting inputs — Jo, O'Neal, Anthony S., Anthony S. 2 accepted; Anthony Spinozzi, Spinozzi, Anthony, Maria de la Cruz, Anthony S. Spinozzi refused. The included roster.html was driven in a real browser against a stand-in database enforcing that same constraint: connect, create a class, paste five names including a deliberate collision, confirm the shortened forms are what reach the database, trigger the refusal on purpose, remove a student, reload, and handle an unreachable database. No unexpected console errors.

What is NOT claimed

• Not tested against a live Supabase project — the browser test used a stand-in that enforces the same rules. Your first real connection is yours to make, and task 5 tells you what a good one looks like.

• Not a secure multi-user system. Anyone with your URL and key can read the roster. That is stated plainly rather than hedged.

• Not a system of record, not a gradebook, not an SIS.

• Not legal advice. Your district's policy, your state's law, FERPA and COPPA are the authorities.

Why the AI is told what not to do so often

Most of the prompts in this pack spend a clause forbidding something — no extra columns, no libraries, no build step. That is not fussiness. Left to itself a model builds what most software looks like, and most software collects more than it needs. Saying no is the part of prompting that nobody teaches.
