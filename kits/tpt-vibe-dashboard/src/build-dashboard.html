Why this build matters

The difference between a page and an app

Build 1 in this series made an activity. This one makes software. One idea separates them.

A page

Forgets everything the moment it closes. Fine for a practice activity a student does once. Useless for anything you want to keep using — you would type your class list in every single morning.

An app

Writes what it knows into the browser's own storage on your device. Close the tab, shut the laptop, come back Thursday: still there.

The technical name is local storage, and that is nearly all you need to know about it.
It is a small notebook the browser keeps for each file on your own machine. Your app writes to it; nothing else can read it; it never leaves the device. No server, no account, no internet.

Why this is the safe option as well as the useful one

Every other way of making something remember involves sending data somewhere — a database, an account, someone's cloud. Local storage is the one option where the question "who else can see this?" has the answer "nobody". For a tool holding a class list, that is not a small detail. It is the whole reason this design is the right one.

What it cannot do, honestly

It is tied to that browser on that device. Open the file on a different laptop and it starts empty. That is a real limit, and it is the same limit that makes it private. Page 18 covers what changing it would cost.

The three tiers, and the names question

Build 1 avoided student data entirely. This one cannot — a name picker needs names. So here is the honest version, which is more useful than a rule that says never.

1

Content you wrote

Questions, timers, group sizes. No student in it. Build freely.

2

De-identified student data

S1, S2, S3 and their scores. The dashboard's export tab produces exactly this. Safe to paste into an AI chat because nobody can be identified from it.

3

Data traceable to a child

Names, and anything attached to them. Whether this is fine or a problem depends entirely on where it lives. That is the point of this page.

The same names, two completely different situations

This file on your laptopThe same file hosted online
Saves only to your browser. Nothing transmitted. No account. No link anyone could visit. About as exposed as the class list in your planner. Now reachable by a URL. Now a record held somewhere, by software your district did not review. Now a conversation with your district, not a setting you flip.
So the rule is not "never use names." It is: names may live locally on your own device; they may not be published, synced, or pasted into a chatbot. The dashboard is built that way on purpose, and the export tab exists so you never have to break it.

Task 2 — the important one

Make it remember

Everything else in this build is ordinary. This is the step that makes it software.

Prompt 2 · saving
Now make this dashboard remember its data between sessions, using the browser's local storage on my own device. Nothing should be sent to a server and there should be no account.

Keep everything in one saved object: the class list, the points for each student, and which students have already been picked.

Important:
• Save whenever anything changes, automatically. I should never press a Save button.
• Load whatever was saved when the page opens.
• If saving or loading fails for any reason, the app must still work with empty data rather than showing an error or a blank screen.
• Show a small "Saved" confirmation so I can see it happening.

Why that fourth bullet is in there

Local storage can be switched off. A private window blocks it, some managed school devices restrict it, and a browser set to clear site data will wipe it. Without that instruction the app can crash on open. With it, the worst case is an empty class list — annoying, not broken. Asking for the failure case is the single most useful habit in this whole series.

Task 2, continued

The test that proves it

Do this exactly

1. Type a name into the class list. Any name.
2. Close the tab completely. Not refresh — close it.
3. Open the file again.

The name should still be there. If it is, you have built an application. If it is not, task 2 is not finished and nothing after this point will work properly.

If the test fails
I closed the tab and reopened the file, and my data was gone. It should have been saved to local storage on this device and loaded again when the page opens. Fix that and give me the whole file back.
Do not move past this page until the test passes. Every later task saves something, and debugging saving while also debugging a points tracker is much harder than debugging saving on its own. This is the one place in the build where patience genuinely pays.

A thing worth knowing

Your data belongs to that file in that browser. Move the file to a different folder and it usually still works; open it in a different browser and it starts fresh. Nothing is lost — you are looking in a different notebook.

Task 3

The class list

Prompt 3 · the roster
In the Class list tab: a text box and an Add button. Typing a name and pressing Add, or pressing Enter, adds that student to a list shown as rounded chips underneath, each with a small x to remove it.

• Adding or removing saves straight away.
• Refuse duplicates and say so, rather than adding the same name twice.
• Removing a student also removes their points and their pick history.
• Show a running count underneath: "24 students".

That third bullet is not fussiness

When a child moves away mid-year and you delete them, their points should go too. Without that instruction their total sits in storage forever and shows up in your export months later. Say what should happen to the data when something is deleted — it is the kind of thing an AI will not decide sensibly on its own.

Task 3 is done when

You can add your real class, reload the page, and they are all still there. At this point the thing is genuinely useful even with four tabs still empty.

Task 4

The fair picker

The one feature here that most bought tools get wrong.

Prompt 4 · fair random
In the Pick a student tab: a big Pick button that shows one student's name in large text.

Add a checkbox called "Fair mode", on by default. When fair mode is on, remember who has already been picked and only choose from students who have not been picked yet. When everyone has had a turn, start a fresh round automatically.

Underneath, show how many students are still to be picked this round. The pick history saves with everything else.

Why this matters more than it sounds

Truly random means the same three children answer everything while two are never asked all week — and you will not notice, because each individual pick looked fair. Fair mode makes participation even by design instead of by your memory. It is the single most defensible thing in this dashboard if a colleague asks why you built your own.

Task 4 is done when

With three names on the list, three picks give you three different students, and the counter goes 2, then 1, then 0 — and the fourth pick starts a new round.

Tasks 5 and 6

Groups and the timer

Prompt 5 · group maker
In the Make groups tab: a number box for group size (default 3) and a Make groups button. It shuffles the whole class properly and deals them into groups of that size, shown as cards side by side.

• Everybody must end up in a group. If the class does not divide evenly, the last group is smaller — never drop anyone.
• Use a proper shuffle, not sorting by a random number.

Why that last line is there

The common quick way to shuffle a list produces uneven results — some arrangements come up far more often than others. Asking for a proper shuffle costs you nothing and means your groups really are random. You do not need to know the algorithm; you just need to have asked for it.

Prompt 6 · timer
In the Timer tab: a big countdown in minutes and seconds, readable from the back of a classroom. Preset buttons for 1, 3, 5 and 10 minutes, plus Start and Pause. When it reaches zero it stops and turns red. It does not need to save between sessions.

Done when

Groups: everyone from your class appears exactly once across the cards. Timer: it counts down, pauses, and turns red at zero.

Points, and the export that keeps you safe

Prompt 7 · points

In the Data and reset tab: a button that builds a copy of the points list with every name replaced by S1, S2, S3 and so on, shown in a text box, plus a Copy button.

Without it, the first time you want AI help spotting a pattern you will be tempted to paste the real list. Tasks 9 and 10

Make it yours, and make it usable by everyone

Prompt 9 · appearance
Restyle it with [your colors] as the main colors. Make the picked name and the timer as large as will fit. Round the corners and give the panels a thick outline so it reads clearly from a distance.
Prompt 10 · accessibility, and this is not optional
Make sure everything works for someone using a keyboard instead of a mouse: every tab and button reachable with Tab, usable with Enter, with a clearly visible outline on whatever is selected. Put the mouse down. Press Tab repeatedly — a clear outline should move between the tabs and buttons. Press Enter on one — it should activate. If either fails, say exactly that and ask again. One more worth adding

The small x that removes a student is an icon with no words. A screen reader announces it as "button" unless you ask for a label. Prompt 10's last line is what turns that into "Remove Ada".

Saving and using it

Out of the chat, into your room

1. Copy all of the code

Use the copy button on the code block. Selecting by hand usually misses the last line.

2. Paste into a plain text editor

Notepad, or TextEdit set to plain text. Not Word — it adds invisible formatting that stops the file working, and the failure is baffling when it happens.

3. Save as dashboard.html

On Windows set "Save as type" to All Files so it does not quietly become a .txt.

4. Put it somewhere you will find it, then leave it there

This matters more than in build 1. Your saved class list is tied to this file in this browser. Pick its home now — desktop, documents, wherever — and do not move it between machines expecting the data to follow.

Make a bookmark. Open the file, then bookmark it like any web page. Now it is one click every morning instead of a hunt through folders, and it will behave like any other tool on your bar.

Using it on the board

Open it at the start of the day and leave the tab open. Press Ctrl and plus (Command and plus on a Mac) a few times to make everything bigger for the room.

When it breaks

The seven things that actually go wrong

1. It opens as a wall of code

The file did not save with .html on the end. Rename it. On Windows turn on file name extensions in File Explorer's View menu so you can see what it really saved as.

2. My class list vanished

Almost always a different browser, a private window, or a browser set to clear site data on exit. Check you are opening it the same way you did before. Nothing is lost — you are looking in a different notebook.

3. It saves, but not on the school laptop

Some managed devices block local storage. If the app still works but forgets, that is the cause — and it is why prompt 2 asked for it to keep working with empty data rather than crash. Ask your tech team; it is usually a policy setting.

4. Fair mode picks someone twice

Say: "Fair mode picked the same student twice before everyone had a turn. It should only choose from students not yet picked this round."

5. The group maker leaves someone out

Say: "Three students were missing from the groups. Everyone must be placed, and the last group can be smaller."

6. The export still shows names

Stop and fix this before using it. Say: "The export still has real names in it. Every name must be replaced with S1, S2, S3 before it is shown." Then check by eye again.

7. It worked, then an edit broke it

Paste the part you changed into the chat and say "something in this is broken, find it." You do not need to spot it yourself.

When you want more

What hosting would cost you

Sooner or later you will want the dashboard on your phone as well as your laptop, or a colleague will ask for a copy that stays in sync. Here is what that actually involves, so you can decide with your eyes open.

What changes the moment it goes online

• The data stops living on your device and starts living on someone's server.
• A link exists that could reach it.
• It becomes software holding student records that your district did not review.
• You, personally, become responsible for something that is properly the school's responsibility.

What to do instead of abandoning the idea

Take it to your technology team as a proposal rather than a surprise. Bring what it does, what data it touches, and where it would live. Districts say yes to reviewed things far more often than to discovered things — and a district that has seen it can host it properly, which is better than you hosting it badly.

The middle option most teachers actually want

Keep it local, and use the export. If you want the same dashboard on two machines, you do not need syncing — you need to retype a class list once a year. That is twenty minutes against a genuine compliance question, and for most people it is not a close call.

The honest summary: everything in this pack is yours, private, and needs nobody's approval. The moment you want it to be in two places at once, it stops being yours alone. That is not a rule someone invented to slow you down — it is just what happens when data moves.

Practical guidance, not legal advice. Your district's policy, your state's student privacy law, FERPA and COPPA are the authorities.

The file

The part that does the remembering

The complete dashboard ships with this pack as classroom-dashboard.html — you do not need to type any of this. This is the piece worth actually looking at, because it is the one you will reuse in everything else you build.

/* ---- storage: one key, this browser only ---------------------------- */ const KEY = 'classroom-dashboard-v1'; const blank = { names: [], points: {}, picked: [] }; let S = load(); function load(){ try { const raw = localStorage.getItem(KEY); if (!raw) return { ...blank }; const o = JSON.parse(raw); return { names: o.names || [], points: o.points || {}, picked: o.picked || [] }; } catch (e) { // private window, blocked storage, corrupt value return { ...blank }; } } function save(){ try { localStorage.setItem(KEY, JSON.stringify(S)); flash('savedMsg', 'Saved'); } catch (e) { flash('savedMsg', 'Could not save on this device'); } } function flash(id, msg){ const el = document.getElementById(id); if (!el) return; el.textContent = msg; setTimeout(function(){ el.textContent = ''; }, 1600); }

Reading it without knowing code

load tries to read what was saved; if anything at all goes wrong it hands back empty data instead of failing. save writes the whole object and shows a confirmation; if the browser refuses, it says so rather than pretending. Both are wrapped in try and catch, which is the instruction from prompt 2 — keep working when storage is unavailable — showing up in the actual file.
